# X-Lab 创新项目入驻与设备协作平台 — 项目介绍

> 课程：《区块链技术应用实践》大作业
> 技术栈：Vue 3 + Go/Gin + Hyperledger Fabric 2.5（CCAAS 部署）
> 在线运行：`./deploy/run.sh fabric` 后访问 `http://127.0.0.1:18088`

## 一、项目背景与问题

浙江大学未来学习中心（X-Lab）管理着一栋楼里的实体空间与设备资源：6 个协作工位、
4 个工程台、大屏区、影视区、录音棚、灵感讨论角、休闲补给站等 18 处空间，以及相机、
工作站、3D 打印机、示波器、录音设备等 28 台设备。项目团队带着 idea 入驻，使用空间
与设备推进作品，结项后退出。

现实中这套资源管理存在三个断裂：

1. **空间靠表格**：谁因为什么 idea 获得了哪些工位、能用到什么时候、承诺产出什么，
   散落在表格和聊天记录里，项目一多就对不上账。
2. **设备靠人记**：设备借出后，谁在什么时候领的、附件齐不齐、归还时状态如何，
   全靠保管人手记，出现争议时无法追溯。
3. **空间与设备不关联**：项目退出时需要同时释放空间**和**核对未归还设备，
   但这两件事往往在不同的人、不同的表里，容易漏。

本系统把三个环节串成**一条可核验的责任链**：所有审批、分配、领取、验收都写入
Hyperledger Fabric 联盟链，每一步留下带组织签名的交易 ID，任何一方都能独立核验，
且审核权与交接确认权通过组织身份（MSP）在链码层强制隔离——越权调用直接被拒绝。

## 二、系统架构

```
浏览器（Vue 3 · Vite · Pinia）
  ├─ 设备协作入口 ──┐
  ├─ 项目入驻与空间 ──┤
  ├─ 管理台（仅 Org1）─┤
  └─ 链上浏览 ──────┘
          ↓ REST API（JSON，Bearer Token 会话）
Go + Gin 后端（:18088，托管前端静态资源）
  ├─ auth.go    会话、角色中间件、按登录用户组织签名
  ├─ store.go   Store 接口：memoryStore（演示）/ fabricStore（Gateway）
  └─ fabric.go  Fabric Gateway 双组织连接（Org1 / Org2 各自证书）
          ↓ gRPC + TLS
Hyperledger Fabric test-network（2 组织 + 1 排序节点，通道 xlabchannel）
  └─ 链码 xlab v1.0（CCAAS 部署，28 个合约函数）
        7 类对象：EQUIPMENT / SPACE / APPLICATION / PROJECT
                 / ALLOCATION / BORROW / ACTIVITY
```

**部署方式**：链码采用 CCAAS（Chaincode-as-a-Service）——自行构建镜像、peer 只连接。
这绕开了本机 Docker 29.x 与 Fabric peer 内置旧版 Docker client 的兼容问题
（详见 README「开发记录」）。

## 三、链上设计

### 对象与键前缀

| 前缀 | 对象 | 说明 |
|---|---|---|
| `EQUIPMENT:` | 设备台账 | 含附件清单、保管人、当前借用单 |
| `SPACE:` | 空间单元 | 含楼层、容量、平面图坐标 |
| `APPLICATION:` | 入驻申请 | idea 摘要 + 哈希、评审结果 |
| `PROJECT:` | 已入驻项目 | 空间、期限、阶段成果、续期次数 |
| `ALLOCATION:` | 空间占用区间 | 起止日期，用于冲突检测 |
| `BORROW:` | 设备交接单 | 申请 / 审批 / 领取 / 归还全程 |
| `ACTIVITY:` | 操作流水 | 每笔操作的审计轨迹（以 TxID 为键） |

### 状态机

**设备借用**：`AVAILABLE → REQUESTED → APPROVED → BORROWED → RETURN_REQUESTED → RETURNED`
（归还验收发现异常转 `EXCEPTION`，处理完毕回 `AVAILABLE`）

**项目入驻**：`SUBMITTED → APPROVED → ACTIVATED（分配空间）→ ACTIVE → CLOSED`
（中途可 `EXTENDED` 续期；评审不通过 `REJECTED`）

### 权限（链码层强制）

| 角色 | 组织 MSP | 可执行 |
|---|---|---|
| 资源管理委员会 | Org1MSP | 台账维护、评审、分配空间、审批借用、交接确认、续期、结项 |
| 入驻项目团队 | Org2MSP | 提交申请、借用申请、提交阶段成果、发起归还 |
| 任何人 | — | 查询（账本公开可核验） |

后端为两个组织各建一份 Gateway 连接，**按登录用户的组织签名提交交易**——
团队的借用申请在链上记为 `Org2MSP`，委员会的审批记为 `Org1MSP`，
调用方身份一目了然。

### 关键业务规则

- **同一设备不能重复借出**：借用时校验设备状态必须为 `AVAILABLE`
- **空间时间不重叠**：按 `SpaceAllocation` 起止日期做区间相交判断（不是布尔占用），
  支持同一工位在不同时段分配给不同项目
- **结项前必须归清设备**：`CloseProject` 统计未归还借用单，大于 0 则拒绝
- **状态机单向流转**：已完成的交接不能修改，更正走追加记录
- **链上链下分离**：链上只存主键、状态、摘要哈希、确认人与时间戳；
  idea 正文、照片、成果文件留在链下

## 四、功能清单

| 模块 | 功能 |
|---|---|
| 登录鉴权 | 管理方 / 团队方双身份，会话 12h，角色路由守卫，接口 403 拦截 |
| 设备协作 | 28 台设备按类别分册、搜索筛选、借用申请、详情页、交接记录、链上历史、逾期标记 |
| 项目入驻 | 楼层平面图（3F/4F）、空间点选偏好、入驻申请、在驻项目列表、待评审队列 |
| 项目详情 | 空间与团队、关联设备、交接记录、阶段成果、续期、结项（含设备核对）、链上历史 |
| 管理台 | 六类待办：入驻评审 / 待分配空间 / 借出审批 / 待领取 / 待验收 / 异常处理 |
| 链上浏览 | 全量交易流水（操作名 + 业务对象名 + 调用方组织 + 时间 + TxID）、交易详情、操作分布、区块视图 |

界面采用顶部导航、深色主视觉与清单式资源台账，使用官方品牌色
（标志蓝 `#0071EF`、品牌青绿 `#43C5AC`）。实景素材包含浙江大学官网图片与
Wikimedia Commons 开放授权图片，详见 `frontend/public/media/credits.json` 和
`docs/media-credits.md`。全站带滚动入场、
数字滚动、指针倾斜、滚动视差与动态媒体；模态框支持键盘焦点管理，动效会响应
系统“减少动态效果”设置。界面已完成 1440 / 768 / 390 三档宽度验收。

## 五、运行方式

```bash
# 完整模式（真实上链）：先起 Fabric 网络，再起服务
./deploy/up.sh          # 部署 test-network + xlabchannel + 链码（CCAAS）
./deploy/run.sh fabric  # 构建前端 → 编译后端 → 单端口 :18088

# 演示模式（不需要 Fabric）
./deploy/run.sh demo    # http://127.0.0.1:18088
```

演示账号：`admin` / `team`，密码均为 `xlab2026`。

一键清场与重建：`./deploy/up.sh down && ./deploy/up.sh`。
